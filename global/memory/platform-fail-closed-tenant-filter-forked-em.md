**Platform prod tenant filter is FAIL-CLOSED and global.** `createMikroOrmConfig` (each service's `mikro-orm.config.ts`) registers `tenant` filter with `default: true` and a `cond()` that THROWS ("filter is active but no tenant context was provided") when no tenant params are seeded. In MikroORM v6, a `default:true` filter with no `entity` restriction fires for EVERY entity — including tenant-exempt ones (e.g. `processed_event`, which has no tenant_id).

**The trap:** an RMQ/event consumer wraps dispatch in `TenantContext.run({tenantId})` (AsyncLocalStorage only) and the handler forks a raw `orm.em.fork()`. Neither seeds MikroORM **filter params** (only `TenantGuard`/`TenantEntityManager`/`TenantFilterInterceptor` do, all HTTP-request-scoped). So the FIRST `em.find`/`findOne` on that forked EM throws → transaction rejects → `nack` → DLQ. The feature is 100% dead in prod.

**Fix:** every read of a tenant-exempt entity from a forked/consumer EM must pass `{ filters: false }` (or `{ filters: { tenant: false } }`) — the `NO_FILTER` convention. Persists/inserts are safe (filters only apply to SELECT).

**Why tests miss it:** `test/testcontainers/setup.ts` registers a NEUTERED tenant filter (`cond: () => ({}), default: false`), so the real fail-closed behaviour is never exercised. A green testcontainer run does NOT prove the tenant-filter path. Guard with a TC that boots the REAL `createMikroOrmConfig` filter (mirror `tenant-filter-enforcement.tc.spec.ts`) and drives the consumer end-to-end.

Found in [[platform-trading-hardening-epic]] #1625 inbox `recordOnce` (expert review, PR #1634); same class as reporting-service #1379. **FIXED in both trading (#1625, backported to epic `a2bde5dc`) and inventory (#1626, `6e055924`) — inbox `findOne` reads now pass `{ filters: false }`.** Independent verifier caught #1626 pre-merge (mergeRecommend=no) exactly as predicted here. NOTE: the guarding tc still boots the NEUTERED filter (setup.ts), so the real-filter path is proven by review, not test — a real-`createMikroOrmConfig`-filter consumer TC (inbox + stock reads end-to-end) remains a pre-main-merge hardening item for the epic.

**SEED-ON-BOOTSTRAP variant (2026-07-03, `fix/deploy-platform-dev` commit `a0b029f5`).** The SAME fail-closed filter also bit `trading-service` `SeedService.onApplicationBootstrap` — the local `npm run platform:up` dev stack crash-looped trading-service (so the gateway never started). TWO distinct throws, in order: (1) `Using global EntityManager instance methods ... disallowed` — the seeder used the raw injected `this.em` (global) instead of forking; (2) once forked, `tenant filter is active but no tenant context` on the `Country` (tenant-SCOPED) read. Fix differs from the consumer case because the reads ARE tenant-scoped, not exempt: **fork (`this.em.fork()`, mirrors auth/tenant/user seeders) AND set the context params (`em.setFilterParams(TENANT_FILTER_NAME, { tenantId })`, mirrors `tenant-guard.ts` / `TenantFilterInterceptor`) before the first read** — do NOT use `{ filters: false }` (that would drop tenant scoping on a scoped entity). General rule for the whole class: **any forked / non-request-scoped EM (consumer, seed, cron, CLI) that reads a `TenantBaseEntity` must establish tenant context first — `{ filters: false }` for tenant-EXEMPT/system reads, `setFilterParams('tenant', { tenantId })` for tenant-SCOPED reads.** The pre-existing seed spec mocked `run()` out (bare EM stub, no `fork`), so it never caught this; the fix adds a regression spec asserting fork + setFilterParams-before-read. Note this branch is even with `origin/main`, so the same latent bug is on `main` — it just hadn't hit main's seed-on-boot path.

**OUTBOX-RELAY + REAPER variant (2026-07-18, PR #1715, #1593/#1707).** The SAME fail-closed filter killed the shared `@acme/event-bus` **`OutboxRelay`** the instant a service enabled it (`enableRelay: true` on auth-service, PR #1707 — see [[platform-deploy-trigger-and-writeback]]). `OutboxEntry` (schema `platform_outbox`) is a platform/cross-tenant table, but the relay polls it on a context-less background timer, so the `default:true` fail-closed `tenant` filter threw on the claim `find` → caught+logged → **NOTHING ever published** (the discovery "email me my workspace links" pipeline dead-ended here, invisibly). **Two sites per class member, and MikroORM v6.6.14 applies filters to `nativeUpdate` too** (verified: `EntityManager.js` processWhere→applyFilters) — so BOTH the `find` AND the Phase-3 status-writeback `nativeUpdate` need `{ filters: { tenant: false } }`, else entries publish but never mark PUBLISHED → infinite duplicate delivery. **The sibling `OutboxReaper`** (stuck-PUBLISHING recovery net, co-wired under the same `enableRelay` gate on the same EM) had the IDENTICAL defect at its own two sites (scan `find` + `flipToFailed` `nativeUpdate`) and was silently defeated on every relay-enabled service — an adversarial review caught it (the relay-only fix was incomplete). Raw `em.execute` SQL queries (advisory lock, backlog count) are filter-EXEMPT (bypass applyFilters) — no disable needed. Meta-rule: **when you fix the fail-closed filter on one query, grep the whole file/dir for EVERY `find`/`findOne`/`count`(ORM, not raw)/`nativeUpdate`/`nativeDelete` on the same platform entity — this class always travels in pairs (read+write) and in siblings (relay+reaper).** Regression guard pattern: a testcontainer test that registers the REAL `tenantFilterDefinition` `default:true` with NO tenant context (not the neutered `setup.ts` filter) and drives the poller end-to-end.
