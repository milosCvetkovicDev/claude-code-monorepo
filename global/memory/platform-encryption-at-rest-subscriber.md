**CONVENTION** for encrypting a recoverable secret column at rest in a Platform NestJS+MikroORM service. Established by auth-service #1282 (PR #1290, epic #1265): `mfa_config.secret` + `oidc_provider.client_secret` → AES-256-GCM. Precedents: accounting-service `ErpTokenEncryptionSubscriber`, platform `TenantSetLocalSubscriber`.

**Pattern = a MikroORM `EventSubscriber`, NOT repository injection.** `getSubscribedEntities()` scopes hooks to the secret-bearing entities only. `beforeCreate`/`beforeUpdate` encrypt; `onLoad` decrypts. Wire via the service's `authMikroOrmOptions(..., subscribers)` → `createMikroOrmConfig` (libs/platform/mikro-orm) MERGES it with `TenantSetLocalSubscriber` (drops neither). Instantiate the subscriber in `app.module.ts` (outside DI — the ORM config factory runs before the Nest container), keyed from the same `ENCRYPTION_KEY` as the DI `SECRET_ENCRYPTOR`. No entity public-API change (read/write the private `_field` via a fixed-literal-per-branch cast to dodge the object-injection lint).

**Three load-bearing correctness rules (each caught by expert review on #1282):**

1. **`onLoad` MUST re-align `helper(entity).__originalEntityData[prop] = plaintext` after decrypt.** MikroORM snapshots the row (ciphertext) BEFORE `onLoad` runs (verified `@mikro-orm/core` 6.6.14: `UnitOfWork.register` sets the snapshot, then `dispatchOnLoadEvent` fires). Skip this and the loaded entity is permanently DIRTY on the secret prop → ANY later flush in the same EM spuriously re-encrypts + rewrites the column with a fresh IV. Best-effort: wrap in try/catch (unmanaged entities in unit tests have no snapshot).
2. **`beforeUpdate` gates on the change-set: `if (propName in args.changeSet.payload)`.** The payload IS keyed by the PROPERTY name (`_secret`), not the column name — confirmed in 6.6.14. (If it were column-keyed, a rotated secret would skip encryption → persist PLAINTEXT.)
3. **Do NOT use a shape heuristic (`looksEncrypted`) to decide whether to encrypt** — a hex-shaped client secret false-positives and gets persisted in the clear. Prevent double-encryption STRUCTURALLY: create=always-plaintext, update=change-set-gated, load=realign-snapshot. `onLoad` must fail CLOSED + LOUD on decrypt failure (log entity id ONLY, never the value; throw) so a legacy-plaintext/corrupt/wrong-key row doesn't crash the load path opaquely.

**Migration = backfill, migrate-then-deploy.** A data migration encrypts existing plaintext rows BEFORE the decrypt-on-load build ships (else GCM auth-tag fails on read; deploy pipeline runs migrations first → default order correct). Reuse the real `AesGcmEncryptionProvider` (single source of truth, no hand-rolled crypto) and use **trial-decrypt** for idempotency (decrypts under our key = already ciphertext → skip; throws = plaintext → encrypt once). `down()` = no-op (decrypting back re-exposes secrets).

**Rotation DELIVERED (#1291, MERGED 2026-06-19)** — the once-missing key-rotation story now exists. Envelope is VERSIONED: `v1:<kid>:<hexIV‖ct‖tag>`, kid = first 8 hex of `SHA-256(derivedKey)` (one-way fingerprint, safe to persist; the `v1:` sentinel is non-hex so it is INCOLLIDABLE with the legacy pure-hex envelope, which still decrypts under the CURRENT key). Provider ctor takes `{ encryptionKey, previousEncryptionKey? }` (optional decrypt-only `ENCRYPTION_KEY_PREVIOUS`, min-32 when set) → builds a kid→key map; `decrypt` selects current|previous by the envelope kid and THROWS on an unknown/retired kid; `isAlreadyCurrent` lets the idempotent re-encrypt migration (auth `Migration_005`; tenant `Migration_004`, which walks the JSONB `integration_credentials` per-value) SKIP already-current rows byte-identical and re-encrypt legacy/previous-key rows. Runbook: `docs/platform/operations/encryption-key-rotation.md`. **Two review-verified operational facts:** (1) KV secrets are PER-SERVICE — `platform-auth-encryption-key` / `platform-tenant-encryption-key` (NOT a shared `platform-encryption-key`); (2) `ENCRYPTION_KEY_PREVIOUS` is NOT yet wired into the charts/ESO → must be provisioned out-of-band BEFORE a rotation, and always migrate-then-rotate (rotate-before-migrate bricks legacy rows: the legacy path decrypts under the current key only).
