Three durable gotchas discovered driving the [[platform-trading-hardening-epic]] pilot (#1625), all in `tests-generate`-produced RED suites for Platform services.

**1. MikroORM raw `getConnection().execute()` requires `?` placeholders, NOT Postgres `$1`/`$2`.** `conn.execute('… WHERE x = $1', [v])` fails at runtime with `there is no parameter "$1"`. Correct: `conn.execute('… WHERE x = ?', [v])` (see auth-service `migration-004-encrypt.tc.spec.ts`). Note: `em.execute('…$1…')` (EntityManager) appears to tolerate `$1` on a different path (shipped accounting-service ERP advisory-lock uses `$1`) — but the raw connection path in tc specs does NOT. Don't infer the raw-conn behavior from `em.execute` usage.

**2. `@cucumber/cucumber` string steps containing `/api/v1/...` ABORT THE WHOLE SUITE at load.** `When('DELETE /api/v1/purchases/:id is called', …)` — Cucumber Expressions treat `/` as the alternation operator; a leading/trailing/space-adjacent `/` makes an empty alternative → `CucumberExpressionError: Alternative may not be empty`, thrown at step-registration in `support_code_library_builder`, before ANY scenario runs. (Note: an _internal_ `EUR/GBP` is a VALID non-empty alternation and does NOT abort — only empty sides do.) **ESCAPE-LEVEL TRAP (cost 2 iterations):** you must write `\\/` in the JS _source_ string, NOT `\/`. In a JS single-quoted literal `'\/'` collapses to `/` at parse time (backslash dropped) → cucumber still sees a bare `/` → still aborts. `'\\/'` → runtime `\/` → cucumber treats it as an escaped literal slash. Verify with `npx cucumber-js -c cucumber.cjs --dry-run` (loads+matches every step, no containers). Also: escape with a CONTENT-level (multiline-aware) pass, not line-anchored — some `When(` defs put the expression on its own line (e.g. a long `filter[traderId]=…` step) and a per-line regex misses them. Regex steps `/^DELETE \/api\/.../ ` are an alternative (but then also escape regex-specials `?` `[` `]`). **This shipped on origin/main via #1471 (`deal-http-gap-fills.steps.ts`), so trading `test:bdd` has NOT been gating in CI** — mirrors [[platform-gateway-integration-suite-rots-undetected]].

**4. New BDD step helpers must find-or-create reference data, not blind-insert.** In trading-service the feature Background `Given I am authenticated as a trader in tenant "…"` runs `ensureReferenceData()` (trading.steps.ts), which seeds Unit `MT` + Currency `GBP`/`EUR` for the default tenant (`00000000-0000-4000-a000-000000000001`). A new seed helper that does `Currency.create({code: GBP, tenantId: <same>})` then hits `currency_code_tenant_id_unique`. Fix: `(await em.findOne(Currency, {code, tenantId}, {filters:false})) ?? Currency.create(...)`. tc-specs (afterEach `clearDatabase`, no auth Background) don't hit this — it only bites in BDD.

**3. "RED verified" via typecheck ALONE is insufficient — RUN the testcontainers.** Typecheck catches import-RED (missing-module) but MISSES: `$1` placeholder errors, cucumber load-aborts, and seed/assertion mismatches (e.g. `SaleLineItem.create()` defaults to DRAFT, so a `seedSaleLineItem(false)` helper that skips `.confirm()` fails a `toBe(CONFIRMED)` assertion regardless of impl). `/pm:tests-generate` output must be exercised with `nx run <svc>:test:integration`/`:test:bdd` before committing the RED baseline and before dispatching GREEN agents.

**Meta-lesson (feedback):** do NOT overrule a subagent's EMPIRICAL claim with static-code analogy — RUN the empirical test first. I denied the agent's correct `$1` finding by reasoning from shipped `$1` code; the tc run proved the agent right. **Why:** empirical > plausible inference, always, for runtime behavior. **How to apply:** when a subagent reports a test failing for reason X and you doubt it, reproduce X yourself before ruling; a 60s test run beats a wrong overrule.
