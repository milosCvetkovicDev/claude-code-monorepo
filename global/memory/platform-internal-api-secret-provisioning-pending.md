#1292 (merged 2026-06-16, PRs #1303 / #1302) wired the auth-service → user-service `/internal/*` calls behind a shared secret `INTERNAL_API_SECRET` (header `x-internal-api-secret`, constant-time compared by user-service `InternalAuthGuard`). The caller is now the canonical `@acme/service-client` `UserServiceClient`.

**Pending operator/infra action:** the Azure Key Vault secret **`platform-internal-api-secret`** must be provisioned — the **SAME value** for **THREE** services (auth-service + user-service + **tenant-service**, each ESO-sync it via `charts/values/{auth,user,tenant}-service.yaml` → env `INTERNAL_API_SECRET`) — **before any prod/staging deploy**. Until it exists those services **fail closed at boot**: `auth.config.ts` / `user.config.ts` / `tenant.config.ts` reject (in production/staging) an absent value, the well-known dev sentinel, OR a value < 32 chars. The fail-closed logic is the shared `@acme/config` helper `refineInternalApiSecret` / `internalApiSecretField` / `transformInternalApiSecret`.

**2026-06-16 — tenant-service ADDED to the consumer set by #1270 (PR #1307, merged):** the auth→tenant `OIDC TENANT_RESOLVER` (`GET /internal/tenants/by-slug/:slug`) is guarded by a tenant-service `InternalAuthGuard` ported from user-service; tenant-service's `TenantConfigSchema` now carries `INTERNAL_API_SECRET` via `internalApiSecretField()` (same fail-closed refine). The previously-anonymous `TenantLimitController` was also retrofitted with the guard. So the KV secret now gates THREE services, not two. **Deploy ordering (load-bearing):** provision the secret + bring the downstream `/internal/*` endpoints (user-service `POST /internal/users` provision; tenant-service `by-slug`) up BEFORE auth-service ships, or OIDC SSO/login fail closed (401/502), not open.

**Dev/test:** no action needed — both default to the shared sentinel `dev-internal-api-secret-change-me-in-prod` (≥32 chars) so local service-to-service calls authenticate.

**2026-06-17 — DEV KV SECRET CREATED (manual interim).** `platform-internal-api-secret` now exists in the dev Key Vault **`development-acme-kv`** (`https://development-acme-kv.vault.azure.net`) — 64 hex chars / 256-bit random, enabled, no expiry, via `az keyvault secret set ... -o none` (value never logged). az CLI is live in the agent sandbox (KV write + list OK; do NOT `secret show` the value — cred-harvest gate). **It is INERT until the chart wiring lands:** the three `charts/values/{auth,user,tenant}-service.yaml` have NO `internal-api-secret` ESO `externalSecret.data` entry nor an `INTERNAL_API_SECRET` env mapping (grep-confirmed), so ESO won't sync it and the services still use the dev sentinel. Nothing is broken — dev currently runs pre-#1303 images without the fail-closed config. The platform-base ESO pattern: each service's `externalSecret.data: [{secretKey, remoteRef.key: platform-*}]` → K8s secret `<svc>-secrets` → `env.valueFrom.secretKeyRef`.
