`platform-auth-service:test` and `platform-user-service:test` are **intermittently flaky in CI** (not locally). Observed 2026-05-29 on PR #928 (#869): two consecutive runs failed on _different_ auth-related projects (run 1 → user-service `LoginUseCase ... publishLogin is not a function`; run 2 → auth-service:test), both **passed locally on the exact HEAD**, and a re-run of the required `main` job went green with **zero code changes**.

**Why:** these specs have time-sensitive assertions (`auth.service.spec.ts` uses `Date.now() + 3600*1000` etc.) that drift under CI load (`NX_PARALLEL=2`, self-hosted runner, often a degraded nx remote cache → `Cache service responded with 400`). Any PR that edits `libs/platform/mikro-orm` (e.g. `tenant-context.ts`) makes **all ~16 platform services "affected"**, so these flaky tests run on every CI attempt even when the PR is unrelated to auth.

**How to apply:** when a platform PR's `main` / `ci / ci` check fails ONLY on `platform-auth-service:test` or `platform-user-service:test`, FIRST reproduce locally (`nx test <project> --skip-nx-cache`) and check whether the project even imports the changed symbol. If green locally + main is green, treat as flake → `gh run rerun <run-id> --failed` rather than editing code. Don't chase it as a regression. Real fix (stabilising the time-based assertions with fake timers) belongs to those services, not to the unrelated PR. Related: [[feedback_reproduce_ci_exact_env]], [[feedback_gha_pod_death_log_truncation]].

**2026-06-08, PR #1192 (sonarqube quality pass, touched only reporting+audit):** the legacy `main` gate failed **twice** on `platform-commission-service:"test:unit"` — a `TradingEventConsumer` reconnect test spewing "RabbitMQ channel closed … 100 reconnect attempts exhausted — manual intervention required", i.e. an **async teardown/reconnect-backoff crash with NO vitest assertion failure** (no `× test` / `AssertionError` anywhere in the log; the group is just marked ❌ on a non-zero worker exit). The **discriminator that proves flake**: `ci / ci` (the Platform gate) ran the same Platform suite and passed **green on the identical commit**, and my changed projects (`platform-reporting-service`, `platform-audit-service`) passed in `main` too. So: when `main` is red on a Platform project the diff doesn't touch (and that project doesn't import the changed code) **while `ci / ci` is green and there's no real assertion**, it's the `main`-gate flake — not a regression. Resolved by `gh pr merge --squash --admin` (override the unrelated red gate) after one re-run also flaked. Note `gh pr merge --delete-branch` hits the worktree quirk ([[feedback_gh_pr_merge_delete_branch_worktree_quirk]]) — the squash + server-side branch delete still succeed; verify deletion via `gh api .../git/refs/heads/<branch>` (404), since `git ls-remote` serves a stale cached advertisement.

**2026-06-16 — residual full-suite flake STILL active post-#1230, AND the `ci / ci`-green discriminator can be unavailable.** On PRs #1302/#1303 (platform-identity follow-ups), `platform-ci-gate` was red across THREE runs with `CI_RESULT: failure`; the per-service `TEST_RESULTS` map showed a **different single random service failing each run** — run 1 `platform-trading-service:"failure"`, run 2 `platform-commission-service:"failure"` (the latter a `TradingEventConsumer` reconnect-teardown crash, no assertion) — every other ~12 services green, and BOTH flaking services **passed locally on the exact HEAD and import none of the changed code** (the PR changed `@acme/config` + `@acme/service-client`; trading/commission only use unchanged `@acme/config` exports). So #1230 reduced but did NOT eliminate the random-per-run full-suite flake. **Critical twist:** the `ci / ci`-green discriminator was UNUSABLE here because the **gateway-image Trivy scan is an embedded STEP (step 12 "Run Trivy vulnerability scanner (gateway)") inside the `ci / ci` job** and hard-aborts it on its 10 HIGH/CRITICAL CVEs → `ci / ci` (hence `platform-ci-gate`) is red on EVERY Platform PR regardless of code, even ones that don't touch the gateway (environmental, also red on `main`). So you can't lean on "`ci / ci` green ⇒ flake". **How to apply:** when `platform-ci-gate` is red, read the resolved `TEST_RESULTS` JSON from the gate job log (`gh run view <run> --log | grep TEST_RESULTS:`) and the `ci / ci` failed STEP names (`gh run view <run> --json jobs`). If the only failed `ci / ci` step is the gateway Trivy AND every `TEST_RESULTS` entry is `success` (or the only failures are services your diff doesn't import, which you reproduce GREEN locally with `nx test:unit <svc> --skip-nx-cache`), it's environmental-Trivy + flake → `gh pr merge <n> --squash --admin` (user-authorized). Re-running shifts the flake to a different service, so don't chase a zero-flake run. Related: [[runner-image-trivy-cve-refresh]], [[distroless-libssl3-cve-pattern]].

**2026-06-19 — the flake class is BROADER than the factory: a HAND-ROLLED vitest config that doesn't use the factory gets neither the #1230 fork-cap NOR a raised testTimeout.** On #1280 (platform-identity event-routing rename) the legacy `main` gate failed THREE times — runs 1 & 3 on `platform-event-bus:test`, run 2 on `platform-gateway:test:unit` + an `ai-service` health spec — every failure a vitest `runWithTimeout` (wall-clock testTimeout) in TIMER-heavy specs (`outbox-relay.spec.ts`, `outbox-reaper.spec.ts`), all GREEN locally, none touching the changed files. Root cause: `libs/platform/event-bus/vitest.config.ts` is a **hand-rolled `defineConfig`** that does NOT import the shared factory (`libs/platform/service-bootstrap/src/testing/vitest-config.ts`, which sets `testTimeout:120s`/`hookTimeout` + the #1230 fork cap), so event-bus ran at vitest's DEFAULT 5s testTimeout → its fake-timer outbox specs time out under CI CPU contention. Compounding: #1280 edited a SIBLING spec in event-bus (`event-handler-explorer.spec.ts`), and `nx affected` runs the WHOLE project's `test` target, dragging in the flaky outbox specs the rename never touched. Fixed in closeout #1339 by adding `testTimeout/hookTimeout: 30s` to event-bus's config (gateway/ai-service already inherit the factory's). **How to apply:** when a Platform project's `:test`/`:test:unit` times out in CI but passes locally, FIRST check whether that project's `vitest.config.ts` uses the service-bootstrap factory — if it's hand-rolled it likely lacks both guards; add `testTimeout: 30_000` (or switch it to the factory) rather than just re-running. #1280 was admin-merged over the flake (user-authorized) since the code was review-verified.

**2026-06-11 — STRUCTURAL FIX LANDED (#1230 / issue #1228), merged to `main` 10:20Z.** Root cause of the `ci / ci` per-service `test:unit` timeouts was finally pinned: **vitest fork oversubscription under `NX_PARALLEL=6`** on the self-hosted runner — Nx ran 6 services in parallel and each vitest spawned its own fork pool, so total forks ≫ 8 cores → a _random_ service (often `platform-trading-service`) timed out per run. Fix = one vitest fork per service in `libs/platform/service-bootstrap/src/testing/vitest-config.ts` (caps `poolOptions.forks.maxForks`/`minForks`), so the per-service suite no longer fights NX*PARALLEL for cores. This is the durable replacement for the "just re-run / admin-merge" guidance above for the **`ci / ci` per-service timeout** class specifically. **How to apply going forward:** if a Platform `test:unit` times out in `ci / ci` \_after* #1230, do NOT just re-run — that's a NEW signal (the fork-oversubscription cause is fixed), investigate it. The legacy `main`-gate full-suite flake (time-based asserts, RMQ-reconnect teardown crash) above is a _separate_ class and may still re-appear; the `ci / ci`-green discriminator still applies to it. Proven by #1221 (deps): red ONLY on `platform-ci-gate` → `platform-trading-service:"failure"` pre-#1230; after update-branch pulled #1230 in, `ci / ci` (15m) + `platform-ci-gate` both green, zero code change. Related: [[platform-dev-stabilization-epic]] (WS — test stability).

## Connection-based flake (distinct from the time-based one) — #1366 (2026-06-22)

NOT only auth/user/event-bus, and NOT only time-based: **trading-service AND commission-service `test:unit` also flake**, but via a DIFFERENT root cause — their unit suites instantiate NestJS consumers/services that open **live redis + RabbitMQ** sockets (`TradingEventConsumer`, kill-switch/cache) instead of mocking the transport. Under no-broker / `--maxWorkers=6` load they crash: signatures `ECONNREFUSED redis://localhost:6379`, `RabbitMQ channel closed — broker still down … 100 reconnect attempts exhausted`, vitest `runWithTimeout`; a fast (~4–9s) worker crash with **zero vitest assertion output**. A `testTimeout` bump does NOT fix this (it's a live-infra dependency, not slowness). Tracked as **#1366** (mock the transport in test:unit).

**Confirm it's a flake (not your change), fast:** the SAME commit passes that service's `test:unit` in the OTHER pipeline (legacy `main` CI vs `platform-ci-gate`/platform pipeline) — if the per-service map names a service whose tree == green main, it's a flake. Clear it with a FULL `gh run rerun <id>` (re-executes the `ci`/test job), NEVER `--failed` (that only re-runs the 5s aggregator gate and re-reads the stale map — see [[feedback_gh_run_watch_lies]]). Hit 3× across 2 services in ONE identity-epic merge train (#1351/#1360 trading, #1362 commission).

## Pact-contracts gate flake + DURABLE FIX (2026-07-01, PR #1533 platform-finance)

The **`ci / pact-contracts`** gate (per-service `test:pact`, wired by #1381, feeds `platform-ci-gate`) flakes the SAME way: a pact-core HTTP mock-server timing race → `Mock server failed … The following request was expected but not received` on a service the PR doesn't touch, **passing 100% locally + on main**, victim VARIES run-to-run (obs: accounting-service one run, auth-service the next — `auth-user-contract.pact.spec.ts > GET /internal/users/by-email`). Same flake class as the unit-test one above, different transport (pact mock server, not RMQ/redis/timers).

**The blindfold applies to pact/integration too** (extends [[platform-ui-test-blindfold-and-icu-casing]]): the shared factory `libs/platform/service-bootstrap/src/testing/vitest-config.ts` did NOT set `reporters`, so `@nx/vite:test` ran only its silent NxReporter → the failing pact suite showed **ZERO output** in CI (just the deprecation warning), only the ❌ group marker. Diagnose-blind is impossible; restore output FIRST.

**Durable fix landed (in the shared factory, benefits every service):**
1. `reporters: ['default']` on the base `test` config → per-spec output streams in CI for unit/integration/pact.
2. `retry: isPact && process.env.CI ? 2 : 0` → **pact-only, CI-only** bounded retry. A genuine contract mismatch fails all 3 attempts deterministically (retry can't mask it — pact assertions are tautological against the declared `builder.jsonBody`), so retry absorbs ONLY the mock-server spawn/timing flake. Local runs get 0 retries so flakes stay visible; integration (testcontainers) gets 0 so real DB failures never retry.

Confirmed: `ci / pact-contracts` went green after the fix (was red 2 consecutive runs). **How to apply:** if pact-contracts reds on a service your diff doesn't touch and it's green locally, it's this flake — the retry now absorbs it; don't chase it. If a pact suite reds with zero output, the reporters fix is already in the factory (a hand-rolled vitest.config that bypasses the factory won't have it — see the event-bus precedent above).
