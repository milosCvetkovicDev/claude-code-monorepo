Full-Platform sleep-determinism guard rollout COMPLETE 2026-06-02 (deferred from #1036). The guard = repo-root `.eslintrc.platform.json`, a `no-restricted-syntax` ban on the real-timer sleep idiom `new Promise(r => setTimeout(r, ms))` in Platform specs + prod `.ts`, opted into per-project via `extends`. Now on ALL 34 Platform app/lib projects: 3 from #1036 + event-bus/mikro-orm (#1087, PR1) + the remaining 29 config-only (#1088, PR2). Carve-outs use `// eslint-disable-next-line no-restricted-syntax -- <reason>`; reasons must be ACCURATE per-site (a reviewer caught one mikro-orm carve-out that mislabeled a single-context rejection test as "concurrent interleaving").

**GOTCHA — the deferred "Option A" (nx.json exclude eslintrc from `test` input) is a NO-OP.** Proven empirically on Nx 22.6.4: `nx affected -t test` derives the affected set from the file→project GRAPH (any file under a project root makes it affected); per-target `inputs` exclusions only change the task CACHE HASH, not the affected set. Adding `!{projectRoot}/.eslintrc.json` to the test input did NOT remove the project from `nx show projects --affected -t test`. Also: editing `nx.json` is a GLOBAL cache-bust (every task re-hashes). So the remembered fix is counterproductive — the robust mitigation for the rollout OOM is SMALL PRs (bounded affected blast-radius), which is what was done. (The #1017 serial per-service `test:unit` accumulator already de-risks the services path.)

**Rotating "memory lottery" flake still trips the REQUIRED `platform-ci-gate`.** On #1088 (config-only, zero runtime change) the gate went red twice, each time isolating a DIFFERENT random service from the per-service map (inventory, then commission) — identical signature: `MaxListenersExceededWarning` (17 exit/SIGINT/SIGTERM listeners, resource pressure) + NO vitest assertion summary (process hit resource limits, didn't fail a test). `ci / ci` itself stayed GREEN both times (the #1017 gate correctly isolated the flaky service). Both flaked services pass `test:unit` LOCALLY. Re-running just re-rolls the lottery (~1 of 13 services flakes per ~17-min run on the single self-hosted runner). → For a config-only PR with ci green, **admin-merge is justified** (`gh pr merge --squash --admin`); document the flake evidence in a PR comment first. This is the same flake class the determinism guard exists to help fix long-term. See [[feedback_platform_auth_user_service_test_flaky]].

So this fix has NO live CI hole today (CI lint is uncached); it guards the cached inferred target used by `nx run-many`/remote-cache/local-dev and is the prerequisite for the eventual CI migration onto the inferred target.
