# Task: List contract fidelity — server-side filters, derived status in list, bounded batch, CSV export

## Description

Bring `GET /api/v1/deals` up to the specified list contract and unblock FE #1446: wire the shipped bracket-filter parser into the endpoint (a filter per list column, including one on the DERIVED status, a couple of related-entity ids, and a `[gte|lte]` date range); expose the derived status in the list payload; add `POST /api/v1/deals/lock-batch` (size capped by config, per-deal result array, partial failure = 200) and `GET /api/v1/deals/export` (CSV honouring active filters). Covers FR-10, FR-13.

## Acceptance Criteria

- [ ] `parseListFilters` wired into the deal controller; prototype-pollution guard behaviour retained (unsafe fields dropped) (AC: 1)
- [ ] A filter on the DERIVED status returns exactly the deals whose derived status matches; the list payload's `status` shows that derived value (AC: 2)
- [ ] A filter on a related-entity id resolves through the child collections it can appear in, not just a direct column (AC: 3)
- [ ] Combined filters + date range + existing sort/pagination compose; p95 < 500 ms against the perf-seed dataset (k6 baseline recorded) (AC: 4)
- [ ] Batch lock: mixed batch → per-deal results (LOCKED / FAILED + errorCode), one `trading.deal.locked` event + activity entry per success, `deal:lock` permission, a batch over the configured cap → 400 (AC: 5)
- [ ] CSV export streams the list's columns for the filtered set under the caller's tenant (AC: 6)
- [ ] `filter[dealNumber]` (eq) supported — the FE routes on the human-facing number, not the surrogate id, so the list has to be filterable by it; list rows also expose the resolved creator name and child-record counts (resolver reuse per ADR-0064) (AC: 7)

## Technical Details

- Derived-status filtering: derive it in the query (aggregate the child statuses there, by the same rules the deriver applies in code) — do NOT denormalise a status column for the sake of the filter; snake_case in any raw SQL.
- Batch lock reuses `LockDealUseCase` per deal (sequential within request, each its own transaction) — no new locking semantics.
- Response shape per architecture §3.3; config `TRADING_MAX_DEALS_PER_LOCK_BATCH` via config helper (never `process.env`).
