# Task: Integration-pipeline observability + tenant-config wiring audit

## Description

Make the trading integration pipeline operable: six Prometheus metric families (outbox lag, consumer redeliveries, parked messages, deal locks, availability rejections, inbound write-backs), OTel span attributes `tenantId`/`dealId` on new paths, a Grafana dashboard + alert rules on the OTel/Mimir stack, and a monitoring-runbook section. Plus FR-15: audit whether `DefaultTenantConfigProvider` actually resolves its per-tenant policy flags from tenant-service — if it is a static stub, implement the real Redis-cached lookup. Covers FR-14, FR-15.

## Acceptance Criteria

- [ ] Metric families emitted per architecture §3.1 naming (trading + `acme_inventory_` mirrors) (AC: 1)
- [ ] Grafana dashboard panels for all six families; alert rules: outbox lag >60s warn />300s crit, parked delta >0 crit, DLQ depth >0 crit, redelivery-rate anomaly warn (AC: 2)
- [ ] Every alert rule proven by a synthetic trigger (documented procedure + evidence) (AC: 3)
- [ ] OTel spans on consumer/handler/lock/stock paths carry `tenantId` + `dealId` attributes (AC: 4)
- [ ] `docs/platform/operations/monitoring-runbook.md` gains a "Trading money pipeline" section (metrics → meaning → response) (AC: 5)
- [ ] Tenant-config audit: evidence of real tenant-service resolution (or an implemented Redis-cached lookup, Redis 6.0-safe commands only) + tc coverage of a policy-flagged tenant end-to-end (AC: 6)

## Technical Details

- Reuse the platform OTel/metrics wiring (ADR-0019 stack); no new observability infrastructure.
- Dashboard/alerts land wherever existing Platform Grafana assets live (follow the repo's established path for dashboards/rules).
- Tenant config: the `TenantConfigProvider` port stays; only the adapter changes if it turns out to be stubbed.
