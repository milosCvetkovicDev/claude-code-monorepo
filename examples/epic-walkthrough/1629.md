# Task: Soft delete + delete/cancel audit across trading aggregates

## Description

Replace physical deletion with compliance-grade soft delete across the trading schema: `deleted_at` column + default-on MikroORM global filter (same mechanism as the tenant filter); convert the 7 existing hard `@Delete` endpoints; add a `DELETE` to the three aggregates that have none, allowed only while a record is still in its initial editable state and refused while live child rows reference it. Deleted rows vanish from ALL reads, from every derived aggregate, and from status derivation; every delete/cancel records an activity entry. Covers FR-8, FR-9.

## Acceptance Criteria

- [ ] `deleted_at` on all trading aggregates + additive migration; global filter registered default-on beside the tenant filter (AC: 1)
- [ ] 7 hard-delete endpoints now set `deleted_at` (row retained in DB), responses unchanged (AC: 2)
- [ ] The new delete on the parent aggregate — initial editable state only, 409 while live child rows reference its line items (AC: 3)
- [ ] The other two new deletes — initial editable state only (AC: 4)
- [ ] Soft-deleted rows excluded from lists, details, name resolution, derived summaries, and status-derivation inputs (tc-proven) (AC: 5)
- [ ] Activity entries recorded for delete and cancel operations (AC: 6)
- [ ] Grep gate: no `em.nativeDelete`/`em.remove` on aggregates outside migrations (AC: 7)

## Technical Details

- `src/common/soft-delete.filter.ts` + entity `softDelete()` methods; filter proven by a dedicated tc suite BEFORE endpoint conversion (architecture §5 rollout).
- Reference-data deletes must also respect referential use — keep the existing FK-safety checks.
- Migration `Migration_007_soft_delete` (renumber to next free at implementation time).
