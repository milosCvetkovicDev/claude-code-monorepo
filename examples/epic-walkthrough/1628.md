# Task: Safe mutations — optimistic locking + Idempotency-Key

## Description

Make every trading mutation safe against lost updates and retries. (a) ADR-0067: MikroORM native version column on all seven mutable aggregates; `version` additive on response DTOs, REQUIRED on mutation DTOs; `OptimisticLockError` → 409 `STALE_WRITE` + `currentVersion`. (b) ADR-0068: `Idempotency-Key` header on the record-creating mutations plus the two lock endpoints, backed by a tenant-scoped `idempotency_key` PG table with stored-response replay, payload-hash mismatch → 409 `IDEMPOTENCY_KEY_REUSE`, TTL cleanup via the existing cron + advisory-lock pattern. Covers FR-6, FR-7.

## Acceptance Criteria

- [ ] Version columns via `@Property({ version: true })` on the 7 aggregates; additive migration lands before DTO enforcement (AC: 1)
- [ ] Stale write (declared version ≠ current) → 409 `STALE_WRITE` with `details.currentVersion`; winner's changes intact (AC: 2)
- [ ] Version increments on every successful mutation incl. lifecycle transitions (AC: 3)
- [ ] Same Idempotency-Key + same payload sent twice → one record, identical responses, `meta.idempotencyReplayed` on replay (AC: 4)
- [ ] Same key + different payload hash → 409 `IDEMPOTENCY_KEY_REUSE` (AC: 5)
- [ ] Expired keys purged by scheduled job (advisory-lock single-instance); store is tenant-scoped (AC: 6)
- [ ] Event consumers / internal transitions unaffected by DTO version requirement (load-then-flush) (AC: 7)
