# Task: Quota-check serialization via PESSIMISTIC_WRITE on the source rows

## Description

Close the verified check-then-act race (ADR-0066): inside every transaction that consumes a line item's remaining allowance, lock all referenced line-item rows with `SELECT … FOR UPDATE` (MikroORM `LockMode.PESSIMISTIC_WRITE`) in deterministic id order BEFORE loading the existing consumers and running the availability check. Concurrent writers against one line item serialize; exactly one of two competing over-allocation attempts fails with 409. Covers FR-5.

## Acceptance Criteria

- [ ] `IPurchaseRepository.findLineItemsForUpdate(ids)` — sorted by id, `PESSIMISTIC_WRITE`, tenant-scoped (AC: 1)
- [ ] The create AND the update path acquire the locks in-transaction before the availability check; no call site remains outside a locked txn (AC: 2)
- [ ] tc race: two parallel writers each claiming 60% of one line item's capacity → exactly one 201, one 409, and the line item ends up with a single claim against it (AC: 3)
- [ ] tc race: a concurrent update-to-80% and create-40% → total allocation never exceeds capacity once both settle (AC: 4)
- [ ] A multi-line write locks in sorted order (deadlock-free under a crossed two-line race) (AC: 5)
- [ ] No regression: single-writer latency change is negligible in existing suites (AC: 6)

## Technical Details

- Locking lives in the repository (architecture §6.4) — services never issue raw locking SQL.
- The availability checker stays a pure domain service; only its call-site context changes.
